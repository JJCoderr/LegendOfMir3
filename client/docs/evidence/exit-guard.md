# 退出限制与死亡豁免

## 原版证据

原版函数0x421F60及其打开/确认调用点见 [退出流程](exit-flow.md)。本批补证：主对象静态基址0x4B9878，加本地人物成员偏移3179944，再加动作字段120，正好是0x7C1E98。因此比较的byte_7C1E98是本地人物动作字段，19对应死亡动作；不是地图状态或网络连接状态。

三个时间字段按检查顺序为人物+0x628E0、+0x628DC、+0x628D4，初始为0。0x415AD0处理31/1309时在0x415D09写第一项；0x418D80在指定技能编号分支0x419017写第二项；0x415F90动作11调用0x417C40，满足其限制时在0x417D2F写第三项。普通行走没有这些写入证据，不能用最后移动时间替代。

## 精确判定

使用Windows GetTickCount的DWORD值，逐项计算无符号32位 `now - tick`。仅当三项全部 **>8000** 才正常放行。动作19无条件豁免等待；18等其他动作不可套用豁免。保留DWORD溢出回绕行为，不改用有符号时间比较。

打开101/109窗口前检查；确认后执行动作前再次检查；直接调用默认退出处理入口也检查，防止绕过。拒绝时不打开/继续退出、不发1009、不结束SceneTree，而是显示CmList1407（当前资源“战斗中无法断开连接。”），前景调色板2、背景3。确认阶段拒绝后对话框关闭，原版通用确认窗口同样在分发结果后清理。

## 当前接入边界

C++ `ExitGuard`封装判定；`set_local_exit_state(action, ticks)`提供解码后状态入口：动作必须0..255，ticks恰好3个DWORD，顺序为628E0/628DC/628D4。先全量校验再应用，非法字段不能只更新动作而意外获得死亡豁免。外部生产者必须使用相同GetTickCount时钟，snapshot的exit_clock用于定向验证。

本批没有把远端人物动作误写为本地退出状态。本地攻击/施法/受击完整消息分发仍缺失，三个时间字段与死亡/复活的自动同步尚未接入；因此当前验证是注入已解码状态的行为验证，不能宣称真实战斗退出限制已端到端完成。换角色、重连和初次登录时状态生命周期也需随本地人物模块统一处理。

## 测试证据

Release构建通过。原生 `--exit-guard`检查8000/8001边界、三项独立限制、DWORD回绕、死亡动作豁免及非死亡动作拒绝。Godot同名场景检查两个窗口入口受限、直接确认入口受限、原版聊天提示、非法字段无部分应用、确认框打开后新动作阻止退出、死亡豁免生成1009。实际截图为exit-guard-blocked.png、exit-guard-death-exemption.png。

回归--exit-request和--exit-dialog均通过，仅覆盖受影响退出模块，不执行其他全场景。退出状态2过渡及角色选择初始页已接入，见exit-transition.md；缓存保存、完整选角/再入场与真实服务端联调仍未完成。
